# Public package 0.12.0 vs MiniSearch 7.2.0

Run of `differential/bench_public.mjs` on 2026-09-26 (UTC) against the 0.12.0 tree
(git HEAD `4a89964` plus uncommitted changes). The [0.10.0 report](2026-09-18-public-vs-original.md)
explains the methodology; compare ratios, not milliseconds across machines.

- 20,000 synthetic documents, 38 queries (`gen_corpus.mjs bench_corpus.json 20000`), options `{"prefix":true,"fuzzy":0.2,"combineWith":"AND"}`
- 9 paired rounds after two warm-ups, medians; "dirty" is a quarter of the documents discarded and not vacuumed
- Node v24.21.0 (win32 x64), AMD Ryzen 9 3900X 12-Core Processor, 64 GiB
- Before timing, 934,016 result rows were compared with MiniSearch's: maximum relative score difference 0

Snapshot sizes (raw / gzip / brotli 6): MiniSearch JSON 8,101 KiB / 2,186 KiB / 1,864 KiB;
native binary 1,077 KiB / 763 KiB / 736 KiB.
Cold module import: MiniSearch 3.7 ms, public package 13.8 ms
(the Node entry compiles the Wasm module on import).

After this run, the native `loadJSONAsync` was changed to wait for a timer
where MiniSearch's loader does (after every 1,000th entry of each map and
posting list, and every 1,000th term) instead of after every 1,000 steps. On
this machine a `setTimeout(0)` wait takes about 15 ms, so both loaders spend
most of their time waiting, and the old yield density made the native loader
take 1.7× MiniSearch's time. Re-measured the same way (5 paired samples,
medians): MiniSearch 8,190 ms, public package 8,332 ms (0.98x). The change
touches only the async loader's yield points; the other rows run the same code.

A paired run of the published 0.11.0 package against this build on the same
machine (7 rounds) measured `search()` 2.37x, `search()` with stored fields
3.18x, `addAll` 2.02x, `loadJSON` 2.54x and `searchJoined` 1.30x faster than
0.11.0; `toBytes` and `loadBytes` took 1.7 ms and 1.8 ms longer (the ids and
stored fields now travel as JSON next to the engine snapshot, which is 1.65x
smaller).
